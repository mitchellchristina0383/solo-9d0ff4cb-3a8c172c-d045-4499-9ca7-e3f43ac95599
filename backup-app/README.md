# 备份链管理 · 中间恢复点清退 + 选择性回退（Flask + SQLite）

一块样例磁盘的**全备 + 按序增量**备份链网页：定长块、内容哈希去重存储；
可按恢复点下载还原镜像；可清退中间恢复点，把仍需保留的块**并入后继增量**，
全程只改指针、不生成临时整盘。
另支持**选择性回退**：选故障前/后两个恢复点并上传当前 RAW 镜像，只把
“两点间有变化且当前值仍等于故障后值”的块换回故障前字节，撤掉误写、
保留后来写到其他块的数据，整盘核对通过才提供回退镜像下载。

## 一、需求与实现对照

| 需求 | 实现 |
| --- | --- |
| 自带样例盘的全备 + 按序增量，定长块存储 | `app/seed.py`：8 块 × 64B，全备 P0 + 增量 P1~P4；块内容存 `blocks` 表，恢复点经 `backup_blocks` 指针引用，按 SHA-256 哈希去重 |
| 选恢复点下载还原镜像 | `GET /backups/<id>/download`，Flask 流式响应，逐块沿链折叠产出，`Content-Length` 固定为整盘大小，不落临时整盘 |
| 缺省块向前继承 | 还原时把 P0..目标点的指针按序折叠，未显式写入的槽位自然保留前一个恢复点的值 |
| 显式清零块还原为零 | 清零用 `is_zero=1` 的标记块表示，与“未写入（继承）”严格区分；还原产出 `\x00 * block_size`。清零后再被写入可“复活” |
| 清退中间点，把仍需保留的块并入后继，不生成临时整盘 | 两阶段：`prepare` 只把待并入槽位写入暂存表 `staged_blocks`；`publish` 在一个 SQLite 事务内把后继缺的槽位指针并入、删除被清退点。块内容因哈希共享保留，零整盘文件 |
| 其余恢复点编号和还原内容保持原样 | 恢复点 UUID 与显示编号 `seq` 终身不变，清退后 seq 出现缺口但不重排；自测对每个存活点逐字节比对清退前后镜像 |
| 合并准备期间仍可从原链还原 | 准备阶段原链一行不改，仅写暂存表；自测与真实 HTTP 均验证准备期间下载内容不变 |
| 重启后使用最后发布的备份链 | 已发布链即唯一持久链；启动时 `recover_pending_jobs` 把所有未发布的 `ready` 任务标记 `stale`，不自动续作 |
| 两次清退基于同一旧链，先发布生效、另一笔提示重试 | `merge_jobs.based_on_version` 记录基线 `chain_version`；发布用 `BEGIN IMMEDIATE` + 版本 CAS，版本不符返回 409「…旧链已失效，请重试」并标记 `stale`；基于新链重新准备即可成功 |
| 选故障前/后两点、上传同尺寸当前 RAW 镜像比对 | `POST /api/revert/prepare` + `POST /api/revert/<id>/image`（请求体即镜像字节）。两点按**继承和清零后的实际字节**比较：快照时把两点沿链折叠成最终指针，指针（哈希+清零标记）不同即字节不同 |
| 只回退“两点间有变化且当前值仍等于故障后值”的块 | `app/revert.py` 逐块比对：当前值==故障后值 → 就地回写故障前字节；当前值==故障前值 → 照留；两点间未变化的块 → 不比对、照留 |
| 与两点都不同的变更块列为冲突 | 冲突块号收集后整盘拒绝：任务置 `failed`、删暂存文件、409 响应体带 `conflicts: [...]`，下载端点对非 `ready` 任务一律 409 |
| 整盘核对通过才提供下载，长度不符/有冲突即拒绝 | 上传先校验字节数（≠ 块数×块大小即 400 并删文件）；有冲突即 409；只有 `ready` 任务的 `/api/revert/<id>/download` 放行 |
| 比对取同一份已提交链上的两点 | `prepare_revert` 在显式一致性读事务里取链版本 + 两点指针并落 `revert_blocks` 快照，`based_on_version` 留档；要求故障前 seq < 故障后 seq |
| 清退照常发布，选中的点随后被清退比对仍可完成 | 快照只依赖 `blocks` 表内容（哈希共享，清退只删指针与恢复点行、不删块内容），`revert_jobs` 不对 `backups` 设外键；清退发布后比对照常完成（T6e 实测） |
| 逐块读取、不整盘载入内存；上传+回退最多暂存一份整盘文件 | 上传用 `request.stream` 按 64KiB 块流式落一份暂存文件（超长即停即拒）；比对只 seek/read 变化槽位并**就地回写同一份文件**；不生成第二份整盘文件 |
| 回退只生成供下载的镜像 | 回退产物仅是 `revert-<id>.img` 下载文件，不改备份链、不改 blocks 表；`POST /api/revert/<id>/discard` 可删除 |
| Docker Compose 启动 | `Dockerfile`（python:3.11-slim + Flask 3.1.3）+ `docker-compose.yml`（命名卷 `backup-data` 持久化 `/data`，回退暂存在其下 `revert/` 子目录） |

### 数据模型（`app/db.py`）

- `meta`：链版本 `chain_version`、块大小、块数
- `backups`：恢复点（UUID、不变 seq、full/inc、标签、时间）
- `blocks`：块内容哈希去重，含一个全局零标记块
- `backup_blocks`：恢复点 → 槽位 → 块指针 + `is_zero`
- `merge_jobs` / `staged_blocks`：清退任务状态机（ready → published / stale）与暂存指针
- `revert_jobs` / `revert_blocks`：回退任务（awaiting_upload → comparing → ready / failed）
  与“两点间有变化”槽位的故障前/后指针快照（只存指针，不存字节）

### 关键并发与一致性

- SQLite 开 WAL、外键、`busy_timeout`；发布事务 `BEGIN IMMEDIATE` 先拿写锁，把并发发布串行化。
- 应用层另限制同时只允许一笔 `ready` 任务，准备即串行；真正的正确性由发布时的版本 CAS 兜底（即使绕过应用层直接插入同基线任务，后发布者仍 409）。
- 每个 HTTP 请求独立连接（`flask.g` + teardown 关闭）；流式下载用专用连接，迭代结束自行关闭。
- 回退快照在显式读事务内完成，两点与链版本取自同一份已提交链；清退发布是原子事务，不会把快照读到“半个新链”。
- 重启恢复：`recover_pending_jobs` 作废未发布的清退；`recover_revert_jobs` 把比对途中（`comparing`）的回退任务置失败并删暂存文件、清理无主 `revert-*.img` 孤儿文件，`ready` 任务与成品镜像（在命名卷内）重启后仍可下载。

## 二、如何运行

### Docker Compose（交付方式）

```bash
cd backup-app
docker compose up --build
# 浏览器打开 http://localhost:8000
```

数据保存在命名卷 `backup-data`（容器内 `/data/backups.db`），`docker compose down`
后再 `up` 仍使用最后发布的链。

### 本地直跑（无 Docker 时，本仓库自测即采用此方式）

```bash
python3 -m pip install -r requirements.txt
export BACKUP_DB=/tmp/backups.db
python3 -m app.server        # http://127.0.0.1:8000
```

### HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 管理页面 |
| GET | `/healthz` | 健康检查 + 当前链版本 |
| GET | `/api/chain` | 链与恢复点列表 |
| GET | `/api/jobs` | 清退任务列表 |
| POST | `/api/backups/<id>/prepare` | 准备清退（写暂存区，201） |
| POST | `/api/jobs/<job_id>/publish` | 原子发布（冲突 409） |
| POST | `/api/jobs/<job_id>/abandon` | 放弃待发布任务 |
| GET | `/backups/<id>/download` | 下载还原镜像 |
| GET | `/api/revert` | 回退任务列表 |
| POST | `/api/revert/prepare` | 创建回退任务：`{"pre_id","post_id"}`，在同一已提交链上快照两点间变化槽位（201） |
| POST | `/api/revert/<id>/image` | 上传当前 RAW 镜像（请求体即字节）并逐块比对、就地回写；通过 200，长度不符 400，冲突 409（响应体带 `conflicts`） |
| GET | `/api/revert/<id>` | 回退任务状态（含回退/照留块数、冲突块号、失败原因） |
| GET | `/api/revert/<id>/download` | 下载回退镜像（仅 `ready` 任务，否则 409） |
| POST | `/api/revert/<id>/discard` | 丢弃任务并删除暂存/成品镜像 |

## 三、实测记录

环境：本机 Python 3.11.2 + Flask 3.1.3（沙箱无 Docker 守护进程，故 Dockerfile/Compose
做了严格 YAML 与编译校验，未实际 build；应用本身在同版本解释器+依赖下完整实测）。

### 1. 自动化自测 `python3 selftest.py` —— 103 项断言全部通过

- **T1 清零/继承**：P0~P4 五个镜像与独立折叠的真值逐字节一致；验证槽位继承、
  P2/P3 清零持续、P4 清零、清零后被 P4 重写“复活”。
- **T2 清退正确性**：清退 P2 并入 P3 后 5→4 点、seq 为 `[0,1,3,4]`（缺口不重排）、
  UUID 不变；四个存活点镜像与清退前逐字节一致；被清退点 404；重复发布 409；
  数据目录无任何 `.img/.tmp` 整盘文件。T2b 再清退 P1，版本 1→2，存活点仍逐字节一致。
- **T3 交错清退**：同基线（v2）两笔任务，先发布者成功（→v3），后发布者 409 且
  提示「请重试」、任务标 `stale`；基于新链重新准备发布成功。
- **T4 中断重启**：独立库先发布一笔（v1），再准备一笔未发布即重连模拟重启，
  `ready` 任务变 `stale`，服务的仍是最后发布的链（编号 `[0,1,3,4]`、各点镜像不变），
  旧任务发布 409，重新发起后成功（→v2）。
- **T5 HTTP 冒烟**：页面 200、下载 `Content-Length=512` 且哈希与真值一致、
  文件名带编号、不存在点 404、清退全备/末端点 409、工厂重启后无 ready 残留且版本保持。
- **T6 选择性回退**：
  - 基本回退 + 清零（pre=P3, post=P4，当前盘==P4）：3 个变化块全部回退，
    结果逐字节等于 P3 镜像——槽 1 回写为全零（显式清零按实际字节回写）、
    槽 6 由零恢复为 A、槽 7 回退为 A；暂存目录恰有一份整盘文件。
  - 照留语义：当前值已等于故障前值的槽 1 照留（`already_pre=1`），两点间未变化的
    槽 2 保留当前自定义值，仅槽 6/7 回退。
  - 末块冲突：末块（槽 7）改成与两点都不同 → 409，响应体 `conflicts=[7]`，
    任务 `failed`，下载 409，暂存文件已删。
  - 长度不符：短（100B）/长（522B）镜像均 400 并说明期望/实收字节数，无文件残留。
  - 比对途中清退：对 P1→P3 建任务后，正常发布清退把**选中的故障前点 P1** 清退
    （链 v0→v1，seqs `[0,2,3,4]`），随后上传比对仍完成，回退 4 块，
    结果逐字节等于 P1 镜像。
  - 参数校验：同点 400、前晚于后 400、不存在 404、缺参 400；任务列表、
    丢弃（删文件）、重复上传 409 均符合预期。
- **T7 回退任务重启恢复**：手工制造 `comparing` 半成品（含半截文件）与孤儿文件，
  重走 `create_app` 启动恢复后半成品置 `failed`、两类文件被清理（计 2 项），
  `ready` 任务重启后仍可下载且内容正确。

### 2. 真实 HTTP 服务（独立进程 + curl/urllib）

- 下载 P4：512B，槽 3、槽 6 为零，槽 1=E、槽 0=D，符合预期。
- 准备期间再次下载，内容与准备前完全一致；第二笔准备被 409 拦截。
- 交错发布实测：API 任务与直接入库伪造的同基线任务，先发布成功 v2→v3，
  后发布返回 `409 链版本已从 2 变为 3，本笔清退依据的旧链已失效，请重试`。
- 中断重启实测（`restart_test.sh`，SIGKILL 后重启）：未发布任务重启后为 `stale`、
  链仍是最后发布版本、旧任务 409、重新清退成功、P4 镜像与真值一致。
- 选择性回退实测（独立进程 + curl `--data-binary` 流式上传）：
  - 清零场景：P3→P4、当前盘==P4 → `reverted=3`，下载 `revert-P3-P4.img` 512B，
    与 P3 真值一致，槽 1 全零、槽 6 恢复为 A、槽 7 回退为 A。
  - 末块冲突：末块改成第三值 → `409 {"conflicts":[7]}`，下载 409，暂存文件删除。
  - 比对途中清退：P1→P3 任务创建后发布清退 P1（链 →v1，seqs `[0,2,3,4]`），
    上传仍 `reverted=4` 通过，结果与 P1 真值一致。
  - 长度不符：100B 上传 → `400 {"expected":512,"got":100}`。

## 四、余项与边界

- **未实际构建/运行镜像**：当前沙箱没有 Docker 守护进程，`docker compose up --build`
  仅做了 compose YAML 解析与 Python 编译校验；需在有 Docker 的环境执行确认。
- **开发服务器**：容器用 Flask 内置服务（单映射端口、演示规模）。生产多进程部署需换
  gunicorn/uwsgi，并保证发布串行化（现依赖单进程 + SQLite 写锁；多 worker 下版本 CAS
  仍正确，但建议加应用级互斥或单写者）。
- **块内容不物理回收**：清退只删指针，哈希共享的块内容保留在 `blocks` 表（题目要求不
  生成临时整盘、强调并入而非重写）。如后续要回收磁盘，可加“无引用块 GC”——但需先
  确认没有 `revert_blocks` 快照仍引用该哈希，并与发布事务同库处理。
- **回退任务为一次性**：长度不符/冲突即终态 `failed`，需重新 `prepare` 再上传；
  成品镜像靠手动 `discard` 或重启清理（仅清半成品与孤儿）释放，未做 TTL 过期。
- **回退快照是指针级**：`revert_blocks` 只存变化槽位的哈希与清零标记，依赖
  “块内容永不删除”这一现状；若未来引入块 GC，需同步考虑快照引用。
- **单盘模型**：样例为一块磁盘的单条链；多盘/多链需在表上增加 disk 维度。
- **鉴权/审计**：演示未加认证与操作审计；合并任务表已保留全部历史（含 stale）可作审计基础。
